# FileHandle

**Purpose & Responsibilities**

`FileHandle` and its subclass `FileHandleReadonly` provide a thin, RAII-based C++ abstraction over POSIX file descriptors. They encapsulate the lifecycle of an open file, ensuring the underlying descriptor is closed upon destruction, and expose high-level operations for seeking, reading, and querying metadata (size, modification time, path).

The design strictly prohibits copying or moving these objects (copy/move constructors and assignment operators are deleted), enforcing a unique ownership model tied to the lifetime of the object instance. The base class `FileHandle` manages the native handle and path, while `FileHandleReadonly` adds synchronous reading capabilities and the ability to duplicate the file descriptor for concurrent access scenarios.

These classes are primarily used by the authentication socket logic (`AuthSocket`) for handling client file transfers and by the patch caching system (`ClientPatchCache`) for verifying file integrity via hashing.

## Member-by-Member Behavior

### Lifecycle and Ownership

*   **`~FileHandle`**: The destructor closes the underlying POSIX file descriptor using `::close()`. This ensures resources are released even if exceptions occur during usage.
*   **`FileHandle` (ctor)**: A protected constructor that initializes the internal state with a file path string and a native file handle. It is protected because `FileHandle` is intended to be instantiated only through derived classes or factory methods outside this unit.
*   **Deleted Operations**: The copy constructor, move constructor, copy assignment, and move assignment operators are explicitly deleted for both `FileHandle` and `FileHandleReadonly`. This prevents accidental duplication of file descriptors, which would lead to double-close errors or resource leaks.

### File Positioning

*   **`Seek`**: Repositions the file read/write offset. It translates the high-level `SeekDirection` enum (`Start`, `Current`, `End`) into POSIX `SEEK_SET`, `SEEK_CUR`, and `SEEK_END` constants respectively. It uses `::lseek()` to perform the operation. If `lseek` fails (returns -1), the assertion `MANGOS_ASSERT` triggers, crashing the server in debug builds or undefined behavior in release builds if assertions are disabled. This implies callers must ensure the seek is valid.

### Metadata Queries

*   **`GetTotalFileSize`**: Retrieves the total size of the file in bytes. It uses `::fstat()` on the native handle. If `fstat` fails, it throws a `std::runtime_error` containing a human-readable error message generated by `SystemErrorToString`.
*   **`GetLastModifyDate`**: Retrieves the last modification time of the file as a `std::chrono::system_clock::time_point`. It also uses `::fstat()`. On failure, it throws a `std::runtime_error` similar to `GetTotalFileSize`. It converts the `st_mtime` (Unix seconds since epoch) into a C++ chrono time point.
*   **`GetFilePath`**: Returns the stored file path string. This is a simple accessor with no side effects.

### Reading and Duplication (`FileHandleReadonly`)

*   **`ReadSync`**: Reads up to `amountToRead` bytes from the file into the buffer `dest`.
    *   It handles partial reads by looping until the requested amount is read or an error/EOF occurs.
    *   It caps each individual `::read()` call to `std::numeric_limits<size_t>::max() - 1` to prevent overflow issues with the `size_t` parameter of `read()`.
    *   If `::read()` returns -1 (error), it logs an error message via `sLog.Out` and returns 0 immediately.
    *   If `::read()` returns fewer bytes than requested (but > 0), it breaks the loop, indicating EOF or a short read.
    *   It returns the total number of bytes successfully read.
*   **`DuplicateFileHandle`**: Creates a duplicate of the current file descriptor using `::dup()`. This allows another part of the system to read from the same file position independently. It returns a `std::unique_ptr<FileHandleReadonly>` wrapping the new descriptor. If `::dup()` fails, it throws a `std::runtime_error`.

## Data Model

This unit does not interact with any database tables. All operations are performed on the local filesystem via POSIX system calls.

## Notable Implementation Details

*   **Assertion in `Seek`**: The `Seek` method uses `MANGOS_ASSERT` instead of returning an error code or throwing an exception. This means that if a seek operation fails (e.g., invalid offset), the server will crash in debug mode or behave unpredictably in release mode. Callers must guarantee the seek is valid.
*   **Partial Read Handling in `ReadSync`**: The loop in `ReadSync` continues until `leftToRead` is 0 or a short read/error occurs. It correctly accumulates the bytes read. However, if `::read()` returns 0 (EOF), the loop breaks, and the function returns the number of bytes read so far. This is consistent with the comment "If return value is smaller than `amountToRead`, the end of file is reached".
*   **Size Limit in `ReadSync`**: The cast `(size_t) std::min(leftToRead, ((uint64_t) std::numeric_limits<size_t>::max()) - 1)` ensures that the argument passed to `::read()` does not exceed the maximum value representable by `size_t`, preventing undefined behavior on 32-bit systems or if `amountToRead` is extremely large.
*   **RAII Compliance**: The destructor always closes the file handle. Since copy/move are deleted, there is no risk of double-closing due to object copies.
*   **Thread Safety**: The methods themselves are not thread-safe with respect to the file descriptor. Concurrent calls to `Seek` or `ReadSync` on the same `FileHandle` instance from different threads will result in race conditions. `DuplicateFileHandle` provides a way to mitigate this by creating independent descriptors.
