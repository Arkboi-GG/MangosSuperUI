# TotemGlebeAI (`totems.cpp`)

## Purpose & Responsibilities

This unit implements the artificial intelligence (AI) for the **Totem of Glebe** creature type within the World of Warcraft emulator. Specifically, it manages the lifecycle of buffs associated with this totem. Its primary responsibility is to ensure that the totem's active buff (`SPELL_BUFF_GLEBE`, ID 8178) is removed if the totem is hit by a spell that is not its own passive aura (`SPELL_BUFF_GLEBE_PASSIVE`, ID 8179) or its main buff. This prevents the totem from retaining its beneficial effects after being disrupted or destroyed by hostile magic.

The unit consists of a single AI class (`TotemGlebeAI`), a factory function to instantiate it, and a registration function to integrate it into the server's script system.

## Member-by-Member Behavior

### `TotemGlebeAI` Class

This class inherits from `TotemAI` and overrides specific behavior to handle spell interactions.

*   **Constructor (`TotemGlebeAI`)**: Initializes the AI object with a pointer to the `Creature` instance representing the totem. It delegates initialization to the base `TotemAI` constructor.
*   **`SpellHit`**: This is the core logic of the unit. It is triggered whenever the totem creature is hit by a spell.
    *   It checks the ID of the incoming spell (`pSpell->Id`).
    *   If the spell ID is **not** `SPELL_BUFF_GLEBE_PASSIVE` (8179) and **not** `SPELL_BUFF_GLEBE` (8178), it assumes the totem has been affected by an external, likely disruptive, spell.
    *   In response, it calls `m_creature->RemoveAurasDueToSpell` twice:
        1.  First, to remove any auras caused by the hitting spell itself (`pSpell->Id`).
        2.  Second, to explicitly remove the totem's own buff (`SPELL_BUFF_GLEBE`).
    *   This ensures that if a player casts a dispel, silence, or damage spell on the totem, the totem's beneficial effect is immediately terminated.

### Factory and Registration Functions

*   **`GetAI_TotemGlebe`**: A global factory function that creates and returns a new instance of `TotemGlebeAI`. It is used by the script system to assign this AI to creatures designated as "TotemGlebe".
*   **`AddSC_Totems`**: Registers the "TotemGlebe" script with the server's `ScriptMgr`. It creates a `Script` object, sets its name to "TotemGlebe", assigns `GetAI_TotemGlebe` as the AI getter, and registers it. This function is called during server startup to load the script.

## Cross-Unit Boundaries

*   **`TotemGlebeAI::TotemGlebeAI`**: Calls the constructor of `TotemAI` (defined in `TotemAI.cpp` or similar). This establishes the inheritance hierarchy, granting the totem basic totem behaviors (such as despawning when the caster dies or moves out of range).
*   **`TotemGlebeAI::SpellHit`**: Calls `Unit::RemoveAurasDueToSpell` (from `Unit.cpp` or `Unit.h`). This is a critical interaction with the core entity system. It relies on the `Unit` class's ability to identify and remove all active auras generated by a specific spell ID. The direction of data flow is from the AI (triggered by a spell event) to the Unit (executing the cleanup).

## Notable Implementation Details

*   **Hardcoded Spell IDs**: The logic depends on two hardcoded spell IDs: `8178` (Buff) and `8179` (Passive). Any change to these spell IDs in the game data would require updating this code.
*   **Aggressive Aura Removal**: The `SpellHit` handler removes the totem's buff (`SPELL_BUFF_GLEBE`) regardless of whether the hitting spell was harmful or benign, as long as it wasn't the totem's own spells. This suggests a design choice where *any* external spell interaction disrupts the totem. For example, if a friendly heal spell accidentally hits the totem, its buff would still be removed. This might be intentional to prevent accidental stacking or persistence, but it is a strict interpretation of "hit."
*   **Double Removal Call**: The code calls `RemoveAurasDueToSpell` for the hitting spell's ID *and* then again for the totem's buff ID. While `RemoveAurasDueToSpell` is likely idempotent or safe to call multiple times, this explicit separation ensures that even if the hitting spell doesn't directly cause the totem's buff to vanish (e.g., via a chain reaction), the buff is forcibly cleaned up.
*   **No State Persistence**: The AI does not track any internal state beyond what is inherited from `TotemAI`. It reacts purely to events.
