# ScriptLoader

**ScriptLoader** is the central registration hub for all custom game scripts within the `wowvmangos` server. Its sole responsibility is to invoke the initialization functions of every individual script module—boss AI, instance logic, zone events, spell overrides, and battleground mechanics—so that they are known to the core engine at startup. It contains no game logic itself; it is purely a wiring layer that connects the core’s script management system to the hundreds of discrete script implementations distributed across the codebase.

The unit consists of two files:
*   `ScriptLoader.h`: Declares the global function `AddScripts`.
*   `ScriptLoader.cpp`: Defines `AddScripts`, which sequentially calls the `AddSC_*` registration functions for every other script unit in the project.

## Purpose & Responsibilities

The primary purpose of **ScriptLoader** is to ensure that all custom scripts are registered with the `ScriptMgr` before the server begins processing game data. In the Mangos/ScriptDev2 architecture, scripts are not automatically discovered; they must explicitly register themselves. `AddScripts` acts as the single entry point for this registration process.

When the server starts, the core framework calls `ScriptMgr::Initialize` (from the `ScriptMgr` unit). As shown in the MAP, `ScriptMgr::Initialize` calls `AddScripts`. Inside `AddScripts`, the code iterates through a massive list of function calls, each corresponding to a different script module (e.g., `AddSC_boss_nefarian`, `AddSC_instance_naxxramas`). Each of these called functions registers its specific handlers (event handlers, AI updates, spell effects) with the core.

If a script module is missing from this list, its logic will never execute, even if the corresponding entities exist in the database. Conversely, adding a new script requires updating this file to include its registration call.

## Member-by-Member Behavior

### **AddScripts**

This is the only member of the unit. It is a void-returning function that performs no conditional logic, error handling, or data manipulation. Its body consists entirely of a sequential list of function calls.

**Behavior:**
1.  **Battlegrounds:** Registers general battleground scripts (`AddSC_battleground`) and specific ones like Alterac Valley (`AddSC_bg_alterac`).
2.  **Custom/Events:** Registers miscellaneous scripts such as `AddSC_zero_scripts` (likely a placeholder or test), `AddSC_ubrs_trash` (Upper Blackrock Spire trash mobs), and world events like `AddSC_elemental_invasions` and `AddSC_war_effort`.
3.  **Eastern Kingdoms Instances & Zones:** Registers scripts for major instances (Blackrock Depths, Deadmines, Gnomeregan, Molten Core, Naxxramas, Scarlet Monastery, Scholomance, Stratholme, Sunken Temple, Uldaman, Zul'Gurub) and their respective bosses. It also registers open-world zone scripts for areas like Elwynn Forest, Stormwind City, and the Plaguelands.
4.  **Kalimdor Instances & Zones:** Registers scripts for Kalimdor instances (Blackfathom Deeps, Maraudon, Onyxia's Lair, Razorfen Downs/Kraul, Ruins/Temple of Ahn'Qiraj, Wailing Caverns, Zul'Farrak) and open-world zones (Ashenvale, Durotar, Silithus, etc.).
5.  **Spells:** Registers class-specific spell override scripts for Druid, Hunter, Mage, Paladin, Priest, Rogue, Shaman, Warlock, and Warrior, as well as item and special spells.

**Notable Implementation Details:**
*   **Commented-Out Scripts:** Several `AddSC_*` calls are commented out in the source code (e.g., `//AddSC_gmisland`, `//AddSC_boss_arena_hardog`, `//AddSC_boss_azshir_the_sleepless`, `//AddSC_boss_kormok`, `//AddSC_boss_grilek`, `//AddSC_boss_hazzarah`, `//AddSC_boss_wushoolay`, `//AddSC_alterac_mountains`). These indicate scripts that are either incomplete, disabled, or temporarily removed from the build. They are declared in the header section of the file but not invoked in the function body.
*   **Order Independence:** The order of calls appears to follow a rough geographical or categorical grouping (Battlegrounds -> Custom -> Eastern Kingdoms -> Kalimdor -> Spells), but there is no explicit dependency between the calls. The registration mechanism likely allows them to be called in any order.
*   **No Return Value:** The function returns `void`. It does not report success or failure. If a called `AddSC_*` function fails internally, it is up to that specific script unit to handle the error (typically by logging or failing silently), as `AddScripts` does not check return codes.

## Cross-Unit Boundaries

**ScriptLoader** exists solely to bridge the gap between the core script manager and the individual script modules.

*   **Called By:** `ScriptMgr::Initialize` (from the `ScriptMgr` unit). This is the trigger point. When the server initializes its scripting subsystem, it invokes `AddScripts` to populate the script registry.
*   **Calls Out:** `AddScripts` calls approximately 150+ distinct `AddSC_*` functions. Each of these functions belongs to a different unit (e.g., `boss_nefarian/AddSC_boss_nefarian`, `instance_naxxramas.Main/AddSC_instance_naxxramas`, `spell_mage/AddSC_mage_spell_scripts`).
    *   **Direction:** Outbound.
    *   **Data Crossing:** None. The calls are fire-and-forget invocations. No parameters are passed, and no return values are captured. The "data" crossing the boundary is the side effect of registration: the target unit adds its handlers to the global script manager.
    *   **Why:** To modularize the codebase. Instead of having one monolithic file containing all game logic, the logic is split into many small files. `ScriptLoader` aggregates them.

## Data Model

**ScriptLoader** does not interact with any database tables. It performs no SQL queries, inserts, or updates. Its operation is entirely in-memory during the server startup phase.

## Notable Implementation Details

1.  **Single Point of Failure for Script Loading:** If `AddScripts` crashes (e.g., due to a linker error or a runtime exception in one of the called `AddSC_*` functions), the entire script subsystem may fail to initialize, potentially causing the server to crash or run without any custom scripts.
2.  **Maintenance Burden:** Adding a new script requires editing this file. Developers must remember to:
    *   Declare the `void AddSC_newscript();` prototype at the top of `ScriptLoader.cpp`.
    *   Call `AddSC_newscript();` inside the `AddScripts()` function body.
    *   Failure to do either results in the script being ignored.
3.  **Commented-Out Code as Documentation:** The commented-out declarations and calls serve as a record of scripts that were once part of the codebase or are planned. For example, `//AddSC_boss_kormok` suggests a Kormok boss script exists in the source tree but is disabled. A maintainer should investigate why these are disabled before re-enabling them.
4.  **No Dynamic Loading:** Scripts are statically linked and registered at startup. There is no support for hot-loading or unloading scripts while the server is running.

## Member Reference

**AddScripts**: The main entry point for registering all custom scripts. It sequentially calls the `AddSC_*` initialization functions for every script module in the project, including battlegrounds, instances, bosses, zones, and spell overrides. It is called by `ScriptMgr::Initialize` during server startup. It contains no logic other than these calls. Several `AddSC_*` calls are commented out, indicating disabled or incomplete scripts.
