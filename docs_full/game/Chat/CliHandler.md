# CliHandler

## Purpose & Responsibilities

`CliHandler` is a specialized subclass of `ChatHandler` designed to execute game server administrative commands from the **server console** (CLI) rather than from an in-game player chat interface.

In the MaNGOS/WowVMangos architecture, `ChatHandler` provides the core logic for parsing command strings, managing permissions, and invoking specific command handlers (e.g., `.reload`, `.npc add`, `.gm online`). However, `ChatHandler` assumes the presence of a `WorldSession` (an active player connection) to handle input/output and context. `CliHandler` overrides this assumption to allow the server process itself to act as the "commander."

Its primary responsibilities are:
1.  **Context Abstraction:** It replaces the dependency on a `WorldSession` with direct access to an account ID and a static access level, allowing commands to run without an associated player character.
2.  **Output Redirection:** It overrides message sending methods to route output to a provided callback function (`Print`), which typically writes to the server's standard output or log file, rather than sending packets to a client.
3.  **Permission Enforcement:** It ensures that console commands respect the RBAC (Role-Based Access Control) system based on the provided account credentials, just as in-game commands would.

It is instantiated by `World/ProcessCliCommands` when a command is entered into the server's interactive console.

## Member-by-Member Behavior

The `CliHandler` class contains only one member defined in this unit: its constructor. All other functionality is inherited from `ChatHandler` or overridden via virtual methods declared in the shared header `Chat.h`.

### Constructor

**`CliHandler(uint32 accountId, AccountTypes accessLevel, void* callbackArg, Print* zprint)`**

This constructor initializes the `CliHandler` instance with the necessary context to operate independently of a player session.

*   **Parameters:**
    *   `accountId`: The numeric ID of the account executing the command. This is stored in `m_accountId` and used by `GetAccountId()` to determine who is issuing the command for logging and permission checks.
    *   `accessLevel`: The security level (e.g., `SEC_ADMINISTRATOR`, `SEC_MODERATOR`) of the account. Stored in `m_loginAccessLevel`. This determines which commands are available.
    *   `callbackArg`: A generic `void*` pointer passed through to the print callback. This allows the caller (typically `World`) to pass context-specific data to the output function if needed.
    *   `zprint`: A function pointer of type `Print` (`void (*)(void*, char const*)`). This is the mechanism for outputting results. Instead of sending network packets, `CliHandler` calls this function to display text.

*   **Initialization:**
    *   It calls the protected default constructor of `ChatHandler` (via the initializer list implicitly, though the syntax `: m_accountId(...)` suggests direct member initialization). Note that the `ChatHandler` protected constructor sets `m_session` to `nullptr`, which is critical because `CliHandler` does not have a session.
    *   It assigns the provided arguments to the private members `m_accountId`, `m_loginAccessLevel`, `m_callbackArg`, and `m_print`.

## Cross-Unit Boundaries

### Called By: `World/ProcessCliCommands`

*   **Direction:** Inbound (Creation)
*   **Collaboration:** The `World` singleton (specifically the `ProcessCliCommands` method) is responsible for reading input from the server console. When a valid command line is detected, `World` instantiates a `CliHandler`.
*   **Data Crossing the Boundary:**
    *   `World` passes the account ID and access level of the user connected to the console (or the default admin account if running in headless mode).
    *   `World` provides a callback function (likely a wrapper around `sLog.outString` or similar) to handle the textual output generated by the command execution.
*   **Why:** This separation allows the complex command parsing and execution logic in `ChatHandler` to be reused for both in-game GMs and server administrators, while `CliHandler` adapts the I/O layer for the non-networked console environment.

### Calls Out: None (Directly)

The `CliHandler` constructor itself does not call out to other units. However, once constructed, the `CliHandler` instance will invoke methods from `ChatHandler` (which may in turn call out to `Database`, `World`, `Player`, etc., depending on the command executed). These downstream calls are part of the `ChatHandler` behavior, not `CliHandler`'s direct responsibility.

## Data Model

`CliHandler` does not interact directly with any database tables. It relies entirely on the `ChatHandler` base class for any database operations required by the commands it executes (e.g., looking up account details, reloading configuration tables). Therefore, no SQL queries or table schemas are specific to this unit.

## Notable Implementation Details

1.  **Null Session Context:**
    The `ChatHandler` base class has a protected default constructor `explicit ChatHandler() : m_session(nullptr)...` specifically intended for CLI subclasses. `CliHandler` uses this path. Many `ChatHandler` methods check `if (m_session)` to determine if they are running in-game or on the console. `CliHandler` ensures `m_session` remains `nullptr`, triggering the console-specific branches in the base class logic.

2.  **Virtual Overrides for Console Compatibility:**
    `CliHandler` overrides several virtual methods from `ChatHandler` to provide console-appropriate behavior:
    *   `GetAccountId()` returns `m_accountId` instead of querying a session.
    *   `GetAccessLevel()` returns `m_loginAccessLevel` instead of querying a session.
    *   `SendSysMessage()` calls `m_print(m_callbackArg, str)` instead of sending a `SMSG_SYSTEM_MESSAGE` packet.
    *   `GetNameLink()` returns an empty string or a plain name, as there is no player object to link to in the chat frame.
    *   `needReportToTarget()` returns `false`, as console commands do not generate chat reports in the same way player interactions do.

3.  **Callback-Based Output:**
    The use of a function pointer `Print* m_print` decouples the command execution from the logging infrastructure. This allows the same `CliHandler` logic to potentially be used in different contexts (e.g., a dedicated admin socket vs. the main server console) by simply providing a different print function.

4.  **Friend Classes:**
    While `CliHandler` inherits from `ChatHandler`, note that `ChatHandler` declares `friend class CombatBotBaseAI`, `PartyBotAI`, and `BattleBotAI`. These friends can access protected members of `ChatHandler` (and thus `CliHandler` if they were to interact with it, though unlikely). This is relevant for understanding visibility but does not change `CliHandler`'s internal logic.

## Member Reference

**`CliHandler`**
Constructor for the CLI command handler. Initializes the handler with a specific account ID, access level, and a callback function for printing output. It sets up the object to operate without a `WorldSession`, enabling the execution of game commands from the server console. It stores the account ID, access level, callback argument, and print function pointer in private members.
