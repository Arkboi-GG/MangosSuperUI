# ChatHandler.Chat

## Purpose & Responsibilities

`ChatHandler.Chat` (implemented in `Chat.cpp` and declared in `Chat.h`) provides the core infrastructure for parsing, validating, and executing administrative and developer commands within the WoWVMaNGOS server. It serves as the central dispatcher for the game’s command-line interface (CLI) and in-game chat commands (prefixed with `.` or `!`).

Its primary responsibilities include:
1.  **Command Registration & Loading:** Maintaining a hierarchical tree of `ChatCommand` structures, merging hardcoded definitions with dynamic overrides from the `command` database table.
2.  **RBAC Integration:** Loading Role-Based Access Control permissions from `rbac_permissions`, `rbac_account_permissions`, and `rbac_command_permissions` to determine command availability beyond simple security levels.
3.  **Parsing & Execution:** Tokenizing input strings, resolving subcommands, checking security/access rights, and invoking the appropriate handler function.
4.  **Argument Extraction:** Providing a suite of utility methods (`ExtractInt32`, `ExtractLinkArg`, etc.) to parse complex arguments, including client-generated "shift-links" (hyperlinks embedded in chat text).
5.  **Output Formatting:** Constructing and sending chat packets (`SMSG_MESSAGECHAT`) or logging output to the console, depending on whether the handler is associated with a `WorldSession` or a CLI context.
6.  **Security Checks:** Enforcing hierarchy rules (e.g., preventing lower-security admins from modifying higher-security accounts) via `HasLowerSecurity`.

This unit does **not** contain the logic for individual commands (e.g., `.go xyz`, `.additem`). Those handlers are defined in other partials of the `ChatHandler` class (e.g., `ChatHandler.TeleportCommands`, `ChatHandler.CharacterCommands`). This unit strictly manages the *mechanics* of how commands are discovered, validated, and dispatched.

## Member-by-Member Behavior

### Initialization & Configuration

*   **`getCommandTable`**: A static method that returns the root of the command hierarchy. It constructs a massive, nested array of `ChatCommand` structs representing all hardcoded commands. If `m_loadCommandTable` is true, it queries the `command` table in the World database to override security levels, help text, and flags for existing commands. It uses `SetDataForCommandInTable` to apply these database overrides. This ensures that administrators can tweak command access without recompiling the server.
*   **`LoadRbacPermissions`**: A static method called during server startup (`World/SetInitialWorldSettings`). It queries the Login database to populate three static maps:
    *   `m_rbacPermissionNames`: Maps permission IDs to names from `rbac_permissions`.
    *   `m_rbacAccountGrantedPermissions`: Maps account IDs to bitmasks of granted permissions from `rbac_account_permissions`.
    *   `m_rbacAccountBannedPermissions`: Maps account IDs to bitmasks of banned permissions.
    It validates that permission IDs are within the valid range (0-31, as they are stored in a 32-bit mask) and logs errors for invalid entries. It then iterates through `rbac_command_permissions` to attach permission masks to specific commands in the command table using `SetPermissionMaskForCommandInTable`.
*   **`SetPermissionMaskForCommandInTable`**: A static helper that finds a command in the table by name and sets its `PermissionMask` bit corresponding to the provided `permissionId`. It handles errors for unknown commands or subcommands that cannot hold permissions.
*   **`SetDataForCommandInTable`**: A static helper used by `getCommandTable` to apply database overrides. It finds the command by name and updates its `SecurityLevel`, `Help`, and `Flags`. It logs discrepancies between hardcoded and database-defined security levels.
*   **`FillFullCommandsName`**: Recursively traverses the command table to populate the `FullName` string for each command (e.g., "go creature"). This is used for logging and help messages.
*   **`CheckIntegrity`**: A debugging tool (currently commented out in `getCommandTable`) that validates the command table structure. It checks for logical errors such as subcommands having lower security than parents, commands having both handlers and children without a default subcommand, or missing handlers.

### Construction & Destruction

*   **`ChatHandler` (ctor)**: Initializes the handler with a `WorldSession*`. Sets `m_sentErrorMessage` to false.
*   **`ChatHandler#2` (ctor)**: Initializes the handler with a `Player*`. It delegates to the session-based constructor by calling `Player.Main/GetSession`.
*   **`ChatHandler#3` (ctor)**: A protected constructor used by subclasses (`CliHandler`, `NullChatHandler`) that takes no arguments, leaving `m_session` as nullptr.
*   **`~ChatHandler` (dtor)**: Default destructor.

### Command Parsing & Dispatch

*   **`ParseCommands`**: The entry point for processing a raw command string.
    *   If `m_session` exists, it verifies the string starts with `.` or `!`. It ignores single dots/exclamation marks.
    *   It checks if the player is allowed to use commands based on security level and server configuration (`CONFIG_BOOL_PLAYER_COMMANDS`).
    *   Crucially, it offloads execution to the main world thread using `World.GetMessager().AddMessage`. This prevents race conditions since chat packets can arrive asynchronously. The lambda captures the text, account ID, and session GUID, verifies the session is still valid and the player is in the world, then creates a local `ChatHandler` and calls `ExecuteCommand`.
    *   If `m_session` is null (CLI), it calls `ExecuteCommand` directly.
*   **`ExecuteCommand`**: The core dispatch logic.
    *   Calls `FindCommand` to locate the `ChatCommand` struct.
    *   Checks `isAvailable` to ensure the user has permission.
    *   Logs the command execution if the security level is above `SEC_PLAYER`.
    *   Invokes the handler function pointer (`command->Handler`).
    *   Handles return values: if the handler returns false (failure) and `HasSentErrorMessage` is false, it sends a default syntax error message and shows help for subcommands if applicable.
*   **`FindCommand` (overloads)**:
    *   The public overload searches the root table.
    *   The protected static overload performs recursive descent through the command tree. It supports abbreviation matching (`hasStringAbbr`) unless `exactlyName` is true. It returns a `ChatCommandSearchResult` indicating success, unknown command, or unknown subcommand. It updates output parameters for the found command, parent command, and remaining text.
*   **`ShowHelpForCommand`** & **`ShowHelpForSubCommands`**: Generate and send help text. `ShowHelpForSubCommands` lists available subcommands for a given command table. `ShowHelpForCommand` finds the command and displays its help text and subcommand list.

### Security & Access Control

*   **`isAvailable`**: Determines if a command is accessible to the current user.
    *   First, it checks if the user's `GetAccessLevel` meets the command's `SecurityLevel`.
    *   If yes, it checks `m_rbacAccountBannedPermissions` to see if the account is explicitly banned from any permission masked to this command.
    *   If the security level is insufficient, it checks `m_rbacAccountGrantedPermissions` to see if the account has been explicitly granted access via RBAC.
*   **`HasLowerSecurity`**: Checks if the target player/account has a lower or equal security level than the issuer. Used to prevent privilege escalation (e.g., a GM banning an Admin).
    *   Resolves the target's session or account ID.
    *   Calls `HasLowerSecurityAccount`.
*   **`HasLowerSecurityAccount`**: Compares security levels.
    *   Respects `CONFIG_BOOL_GM_LOWER_SECURITY`. If disabled, non-player sessions (console) cannot target players with equal or higher security unless `strong` is true.
    *   Returns true (indicating failure to proceed) if the issuer's security is lower than the target's, or if `strong` is true and they are equal. Sends `LANG_YOURS_SECURITY_IS_LOW` and sets the error message flag.

### Output & Messaging

*   **`SendSysMessage`**: Sends a system message to the session.
    *   Copies the string to prevent corruption by `strtok` in `LineFromMessage`.
    *   Splits the message by newlines.
    *   For each line, calls `BuildChatPacket` with `CHAT_MSG_SYSTEM` and sends the packet via `m_session->SendPacket`.
    *   Sets `m_sentErrorMessage` to true.
*   **`SendGlobalSysMessage`**: Similar to `SendSysMessage`, but broadcasts the packet to all connected clients via `sWorld.SendGlobalMessage`.
*   **`PSendSysMessage` (overloads)**: Variadic versions of `SendSysMessage` that format strings using `vsnprintf` before sending. Supports both raw format strings and `mangos_string` IDs.
*   **`PGetParseString`**: Formats a `mangos_string` ID with variadic arguments and returns the resulting `std::string`. Useful for constructing messages that need further processing before sending.
*   **`BuildChatPacket`**: A static utility that constructs an `SMSG_MESSAGECHAT` packet. It handles the complex serialization requirements for different chat types (Say, Whisper, Monster Say, Channel, etc.), including sender/target GUIDs, names, and language codes.
*   **`LineFromMessage`**: A static helper that uses `strtok` to split a message buffer by newline characters.

### Argument Extraction Utilities

These methods parse the `char*` argument string passed to command handlers. They generally advance the pointer to the next unparsed token.

*   **`SkipWhiteSpaces`**: Advances the pointer past whitespace characters.
*   **`ExtractInt32` / `ExtractOptInt32`**: Parses a signed 32-bit integer. `Opt` versions use a default value if the argument is empty.
*   **`ExtractUInt32` / `ExtractOptUInt32` / `ExtractUInt32Base`**: Parses an unsigned 32-bit integer. `Base` allows specifying the radix (e.g., 16 for hex).
*   **`ExtractFloat` / `ExtractOptFloat`**: Parses a floating-point number.
*   **`ExtractLiteralArg`**: Extracts a string token delimited by whitespace. Rejects quoted strings and links. Optionally validates against a prefix literal.
*   **`ExtractQuotedArg`**: Extracts a string enclosed in quotes (`'`, `"`, or `[]`).
*   **`ExtractQuotedOrLiteralArg`**: Attempts `ExtractQuotedArg` first, then `ExtractLiteralArg`.
*   **`ExtractOnOff`**: Parses "on"/"off" literals into a boolean.
*   **`ExtractLinkArg`**: Parses complex client-side shift-links (e.g., `|cffffffff|Hitem:123:0:0:0:0:0:0:0|h[Item Name]|h|r`). It extracts the link type, key, and optional data fields.
*   **`ExtractArg`**: Combines `ExtractQuotedOrLiteralArg` and `ExtractLinkArg` to handle most standard arguments.
*   **`ExtractOptNotLastArg`**: Extracts an argument only if there are more tokens following it.
*   **`ExtractKeyFromLink`**: Specialized parser for shift-links, returning the key portion. Supports multiple link types.
*   **`ExtractKeyFromLink#2`**: An overload of `ExtractKeyFromLink` that accepts a single `linkType` string instead of an array, simplifying calls when only one link type is expected.
*   **`ExtractUint32KeyFromLink`**: Extracts a uint32 key from a shift-link of a specific type.
*   **`ExtractSpellIdFromLink`**: Handles spell, talent, and enchant links, resolving them to a valid spell ID.
*   **`ExtractGameTeleFromLink`**: Resolves teleport links to a `GameTele` struct.
*   **`ExtractGuidFromLink`**: Resolves player, creature, or gameobject links to an `ObjectGuid`.
*   **`ExtractLocationFromLink`**: Resolves various location links (player, teleport, taxi, creature, gameobject, area trigger) to map ID and coordinates (x, y, z).
*   **`ExtractPlayerNameFromLink`**: Extracts a player name from a player link.
*   **`ExtractPlayerTarget`**: A high-level utility that resolves a target player from arguments (name, link, or selection). It populates `Player*`, `ObjectGuid`, and `std::string` outputs.
*   **`ExtractAccountId`**: Resolves an account ID from a name, numeric ID, or selected player.
*   **`ExtractRaceMask`**: Parses race names or masks (e.g., "alliance", "horde", "human") into a bitmask.

### Target Resolution

*   **`GetSelectedPlayer`**: Returns the `Player*` of the currently selected unit, or the issuer's player if nothing is selected.
*   **`GetSelectedUnit`**: Returns the `Unit*` of the currently selected unit, or the issuer's player.
*   **`GetSelectedCreature`**: Returns the `Creature*` of the currently selected unit.
*   **`GetSelectedPet`**: Returns the `Pet*` of the currently selected unit.
*   **`GetGameObjectWithGuid`**: Retrieves a `GameObject` from the map using a low GUID and entry ID.

## Data Model

This unit interacts with the following database tables:

*   **`command`** (World Database):
    *   Used by `getCommandTable`.
    *   Columns accessed: `name` (to identify the command), `security` (to override access level), `help` (to override help text), `flags` (to override command flags).
    *   Purpose: Allows dynamic configuration of command access and help text without code changes.

*   **`rbac_permissions`** (Login Database):
    *   Used by `LoadRbacPermissions`.
    *   Columns accessed: `id` (permission ID), `name` (permission name).
    *   Purpose: Defines the available permissions in the RBAC system.

*   **`rbac_account_permissions`** (Login Database):
    *   Used by `LoadRbacPermissions`.
    *   Columns accessed: `account_id`, `permission_id`, `granted`.
    *   Purpose: Maps permissions to specific accounts, either granting or banning them.

*   **`rbac_command_permissions`** (Login Database):
    *   Used by `LoadRbacPermissions`.
    *   Columns accessed: `command`, `permission_id`.
    *   Purpose: Links specific commands to RBAC permissions, allowing fine-grained access control.

## Notable Implementation Details

*   **Thread Safety in `ParseCommands`**: Chat packets can be processed on network threads. `ParseCommands` detects if a session exists and, if so, queues the command execution to the main world thread via `World.GetMessager().AddMessage`. This is critical because command handlers often modify game state (players, objects) which must be done on the main thread. The lambda captures the session GUID and account ID to verify the session is still valid when the task executes, preventing use-after-free bugs if the player disconnects.
*   **Shift-Link Parsing Complexity**: `ExtractLinkArg` and related functions implement a robust parser for client-generated hyperlinks. These links have a specific format (`|c[color]|H[type]:[key]:[data]|h[name]|h|r`). The parser handles optional color codes, various link types, and nested data. `isValidChatMessage` performs strict validation of these links to prevent security issues, ensuring that item colors match quality, spell names match IDs, etc.
*   **RBAC Mask Limitation**: The RBAC system uses a 32-bit integer mask for permissions. Consequently, `LoadRbacPermissions` enforces that permission IDs must be less than 32. If a permission ID >= 32 is found in the database, it is logged as an error and ignored. This limits the system to 32 distinct permissions.
*   **Command Table Integrity**: The `CheckIntegrity` function, though currently commented out, highlights design constraints: subcommands cannot have lower security than their parent, and commands with children must have a default subcommand (empty name) if they also have a handler. This enforces a consistent command structure.
*   **Error Message Suppression**: The `m_sentErrorMessage` flag allows command handlers to suppress the default "syntax error" message if they have already sent a specific error message. This prevents confusing duplicate output.
*   **Abbreviation Support**: `FindCommand` supports abbreviated command names (e.g., `.g` for `.go`) via `hasStringAbbr`, unless `exactlyName` is forced (used for database overrides). This improves usability for administrators.
*   **Static State**: The command table and RBAC maps are static members. They are initialized once at startup. `m_loadCommandTable` ensures the database query only happens once.
