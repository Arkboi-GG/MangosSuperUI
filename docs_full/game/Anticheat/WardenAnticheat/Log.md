# Log

The `Log` class is the centralized, singleton-based logging infrastructure for the VMaNGOS server, managing the routing, filtering, formatting, and output of diagnostic, operational, and anti-cheat messages to the console, filesystem, and database interfaces.

It serves two distinct but integrated roles:
1.  **General Server Logging (`Log.Main`):** Handles multi-destination output (console, specialized log files), hierarchical severity filtering, feature-specific bitmask filtering, and "smart logging" for targeted debugging of specific entities.
2.  **Warden Anti-Cheat Logging (`Log.Warden`):** Implements the server-side protocol for the Warden anti-cheat system, including cryptographic handshakes, module distribution, integrity scan orchestration, and penalty enforcement (kicks/bans).

## How the Class is Split

The class is implemented across two partials, each handling a distinct domain of logging and security:

### Log.Main
**Responsibility:** General-purpose logging infrastructure.
This partial owns the core `Log` singleton, including initialization, configuration parsing, file management, and output formatting. It provides the primary API (`Out`, `OutConsole`, `OutFile`) used by nearly every other unit in the codebase. Key members include:
*   **Initialization:** `Log()`, `OpenWorldLogFiles()`, `InitSmartlogEntries()`, `InitSmartlogGuids()`.
*   **Filtering & Levels:** `HasLogFilter()`, `SetLogFilter()`, `HasLogLevelOrHigher()`, `Get/SetConsole/File/DbLevel()`.
*   **Output:** `Out()`, `OutConsole()`, `OutFile()`, `SetColor()`, `ResetColor()`.
*   **Utilities:** `OpenLogFile()`, `WaitBeforeContinueIfNeed()`, `IsSmartLog()`.

### Log.Warden
**Responsibility:** Warden anti-cheat protocol and enforcement.
This partial implements the `Warden` class (often referred to as `Log.Warden` in the map due to file location) which manages per-session anti-cheat state. It handles secure communication, scan scheduling, and penalty application. Key members include:
*   **Protocol & Crypto:** `Warden()` (ctor), `RequestChallenge()`, `HandleChallengeResponse()`, `EncryptData()`, `DecryptData()`.
*   **Module Management:** `SendModuleUse()`, `SendModuleToClient()`.
*   **Scan Orchestration:** `SelectScans()`, `EnqueueScans()`, `RequestScans()`, `ReadScanResults()`.
*   **Enforcement:** `ApplyPenalty()`, `KickSession()`, `LogPositiveToDB()`.
*   **Integration:** `OutWarden()` (specialized logging), `LoadScriptedScans()`.

## How the Partials Collaborate

The collaboration between `Log.Main` and `Log.Warden` is primarily unidirectional, with `Log.Warden` relying on `Log.Main` for output, while `Log.Warden` operates independently regarding its state machine and protocol logic.

*   **Logging Dependency:** `Log.Warden/OutWarden` calls `Log.Main` methods (`OutTime`, `OutTimestamp`, `SetColor`, `ResetColor`) to format and emit Warden-specific logs. This ensures Warden activity appears in the same log files and console streams as general server activity, tagged with account context.
*   **No Shared State:** There is no shared mutable state between the two partials. `Log.Main` is a global singleton accessed via `sLog`, while `Log.Warden` instances are created per-player session.
*   **External Boundaries:**
    *   **`Log.Main`** is called by virtually all units (`Creature`, `Spell`, `Player`, `Map`, `AiBotAI`, etc.) for diagnostic output. It reads configuration from `World` and writes to the filesystem.
    *   **`Log.Warden`** is driven by the `Anticheat` manager (`Anticheat/UpdateWardenSessions` calls `Update`). It interacts with `WorldSession` for packet I/O and `World` for penalties (bans/kicks) and configuration. It collaborates with `WardenWin`/`WardenMac` for platform-specific scan logic and `WardenScanMgr` for scan selection.

## Data Model

The `Log` class does not directly query or mutate database tables for its core functionality.

*   **`Log.Main`:** Writes to the filesystem (log files) and standard I/O. It does not execute SQL. The MAP reference to `realmd_Main/main` in `OpenWorldLogFiles` is an artifact; no SQL is executed. Database logging is handled by other units (e.g., `DatabaseMysql`) which may check `Log::GetDbLevel` but perform their own SQL.
*   **`Log.Warden`:** Does not directly interact with database tables. `LogPositiveToDB` is a stub that logs to console/file but does not execute SQL. Penalties (bans) are enforced via `World/BanAccount`, which interacts with the `account_banned` table, but this interaction is abstracted away from the `Warden` class.

## Where to Go Deeper

*   **For general logging configuration, file management, and smart logging:** See **Log.Main**. This doc covers how to configure log levels, filters, smart-log entries/GUIDs, and understand the output format.
*   **For Warden anti-cheat protocol, scan orchestration, and penalty enforcement:** See **Log.Warden**. This doc details the cryptographic handshake, module distribution, scan selection logic, and how penalties are applied.
