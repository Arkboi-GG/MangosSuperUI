## Purpose & Responsibilities

`ThreatManagerEvent` is a lightweight data structure within the `wowvmangos` event system, specifically designed to carry context for high-level threat management operations. It inherits from `ThreatRefStatusChangeEvent`, which in turn inherits from `UnitBaseEvent`.

Its primary responsibility is to associate a specific `ThreatContainer` instance with an event type defined in the `UnitThreatEventType` enum. This allows the event dispatcher or handler to know not just *what* happened (e.g., "sort the list" or "set next target"), but *where* it happened (which container holds the threat data). It is part of the broader AI threat tracking subsystem, managing how creatures prioritize targets based on threat levels generated by players and pets.

Unlike `ThreatRefStatusChangeEvent`, which deals with individual `HostileReference` updates (like a player gaining threat or going offline), `ThreatManagerEvent` operates at the aggregate level of the entire threat list managed by a `ThreatManager`.

## Member-by-Member Behavior

The class consists of two constructors and two accessor methods for its private member `iThreatContainer`.

### Construction
*   **`ThreatManagerEvent(uint32 pType)`**: Initializes the event with a specific type mask (from `UnitThreatEventType`). It delegates to the base class constructor `ThreatRefStatusChangeEvent(uint32)`, passing the type. It initializes the private `iThreatContainer` pointer to `nullptr`. This constructor is likely used for events that do not immediately require a specific hostile reference but still need to be associated with a container later.
*   **`ThreatManagerEvent(uint32 pType, HostileReference* pHostileReference)`**: Similar to the first constructor, but also accepts a `HostileReference*`. It delegates to `ThreatRefStatusChangeEvent(uint32, HostileReference*)`, passing both the type and the reference. The `iThreatContainer` is still initialized to `nullptr`. This allows the event to carry information about a specific entity involved in the threat change, while still being prepared to hold the container context.

### Accessors
*   **`setThreatContainer(ThreatContainer* pThreatContainer)`**: Sets the internal `iThreatContainer` pointer to the provided value. This method is crucial for binding the event to the specific threat list it pertains to before the event is processed.
*   **`getThreatContainer()`**: Returns the stored `ThreatContainer*` pointer. This allows event handlers to retrieve the correct container to perform operations like sorting or target selection.

## Data Model

This unit does not interact directly with any database tables. It operates entirely in memory, manipulating pointers to in-memory objects (`ThreatContainer`, `HostileReference`, `ThreatManager`).

## Notable Implementation Details

1.  **Inheritance Chain**: `ThreatManagerEvent` extends `ThreatRefStatusChangeEvent`. This means it inherits the ability to store a `HostileReference*` and various typed values (`iFValue`, `iIValue`, `iBValue`) via a union. However, `ThreatManagerEvent` does not add any new value storage; it only adds the `ThreatContainer*`. This suggests that while the event is tied to a specific container, it might also carry context about a specific reference (e.g., the player who caused the sort) or a value (e.g., a threshold), though the constructors provided do not initialize these inherited fields beyond the reference.
2.  **Null Initialization**: Both constructors explicitly initialize `iThreatContainer` to `nullptr`. This implies that `setThreatContainer` must be called before `getThreatContainer` is safely used, or that the event system handles null containers gracefully.
3.  **Event Types**: The class is designed to work with the `UnitThreatEventType` enum. Specifically, the macros `UEV_THREAT_MANAGER_EVENT_MASK` include `UEV_THREAT_SORT_LIST`, `UEV_THREAT_SET_NEXT_TARGET`, and `UEV_THREAT_VICTIM_CHANGED`. These are the likely types passed to the `ThreatManagerEvent` constructors.
4.  **Memory Safety**: As with all pointer-based event systems in C++, care must be taken to ensure that the `ThreatContainer*` and `HostileReference*` remain valid for the duration of the event's lifecycle. If the event is queued and processed asynchronously, dangling pointers could lead to crashes. The code provides no automatic lifetime management for these pointers.
