# BoundsTrait

`BoundsTrait` is the geometric abstraction layer for the VMaNGOS Virtual Map (VMap) system, providing specialized interfaces that allow spatial acceleration structures (Bounding Interval Hierarchies and Grids) to interact with diverse 3D model types. It bridges the gap between generic collision algorithms and specific data representations—handling dynamic entities (`GameObjectModel`), static world geometry (`WorldModel`/`GroupModel`), and raw asset conversion (`ModelSpawn`)—without exposing the underlying memory layouts to the spatial indexing logic.

The class is split across three partials, each addressing a distinct phase of the collision lifecycle: runtime dynamic indexing, offline asset compilation, and runtime static geometry representation.

## How the class is split

### BoundsTrait.DynamicTree
**Responsibility:** Runtime spatial indexing for dynamic objects.
This partial implements the `DynamicMapTree`, a high-performance spatial index for `GameObjectModel` instances (players, NPCs, movable props). It uses a hybrid `RegularGrid2D` and `BIHWrap` structure to manage insertion, removal, and query operations. Key members include the `DynTreeImpl` internal state manager, which handles periodic rebalancing via `ShortTimeTracker`, and a suite of intersection callbacks (`DynamicTreeIntersectionCallback`, etc.) that translate generic ray-cast queries into specific `GameObjectModel` intersection tests. It exposes methods like `insert`, `remove`, `isInLineOfSight`, and `getHeight` to the rest of the engine.

### BoundsTrait.TileAssembler
**Responsibility:** Offline conversion of raw assets to optimized binary formats.
This partial contains the `TileAssembler` utility, which runs during map compilation (not at runtime). It reads raw extracted model data (`dir_bin`, raw M2/WMO files) and converts it into the binary `.vmtree`, `.vmtile`, and `.vmo` files consumed by the server. Key members include `convertWorld2` (the main pipeline orchestrator), `readMapSpawns` (parsing spawn records), `calculateTransformedBound` (computing bounds for M2 models lacking pre-calculated data), and `convertRawFile` (serializing `WorldModel` structures). It interacts heavily with `BIH` construction and `ModelPosition` transformations.

### BoundsTrait.WorldModel
**Responsibility:** Runtime representation and collision logic for static geometry.
This partial defines the core static model classes: `WorldModel` (entire buildings/terrain chunks), `GroupModel` (individual mesh groups within a model), and `WmoLiquid` (liquid surfaces). It provides the geometric primitives for collision detection, such as `IntersectTriangle` (Möller–Trumbore algorithm), `IsGoingOut` (winding order checks), and various callback functors (`GModelRayCallback`, `WModelRayCallBack`) used by BIH traversals. It handles serialization/deserialization (`readFile`, `writeFile`) and specific queries like `GetLiquidLevel` and `IsUnderObject`.

## How the partials collaborate

The collaboration follows a strict **Offline-to-Online** data flow:

1.  **Compilation Phase (`TileAssembler` → `WorldModel`):**
    During map preparation, `BoundsTrait.TileAssembler` reads raw game assets. It instantiates `BoundsTrait.WorldModel` objects (`WorldModel`, `GroupModel`, `WmoLiquid`) to hold the geometry in memory. `TileAssembler::convertRawFile` populates these objects with mesh data and liquid information, then serializes them into binary files. `TileAssembler` also uses `BoundsTrait.WorldModel`'s `getBounds` trait to build the initial BIH structures for the static maps.

2.  **Runtime Loading (`WorldModel` ← `MapTree`/`VMapManager2`):**
    At server startup, the engine loads the binary files generated by `TileAssembler`. `BoundsTrait.WorldModel::readFile` deserializes the data back into `WorldModel` and `GroupModel` instances. These instances are then managed by `MapTree` and `VMapManager2` for static collision queries.

3.  **Runtime Dynamic Queries (`DynamicTree` ↔ `Map.Main`):**
    Independently of static geometry, `BoundsTrait.DynamicTree` manages dynamic objects. `Map.Main` inserts/removes `GameObjectModel` instances into the `DynamicMapTree`. When a collision query occurs (e.g., Line of Sight), the engine may query both the static `WorldModel` trees (via `VMapManager2`) and the dynamic `DynamicMapTree`. The `DynamicTree` callbacks delegate to `GameObjectModel::intersectRay`, while `WorldModel` callbacks delegate to `GroupModel::IntersectRay`.

4.  **Shared Geometric Primitives:**
    All three partials rely on the same underlying geometric concepts (AABBs, Ray-Triangle intersection) but implement them differently for their specific data types. `DynamicTree` uses pointer-based hashing for dynamic objects, while `WorldModel` uses vertex-based bounds for static meshes.

## Data model

This class does not interact with any SQL database tables. All data is either:
*   **In-memory runtime state:** Held by `DynamicMapTree` (dynamic objects) and `WorldModel`/`GroupModel` instances (static geometry loaded from disk).
*   **Binary files:** Generated by `TileAssembler` (`.vmtree`, `.vmtile`, `.vmo`) and consumed by the runtime loader.

## Where to go deeper

*   **For dynamic collision tuning:** Open **BoundsTrait.DynamicTree** to understand how `GameObjectModel` instances are indexed, how rebalancing is triggered (`CHECK_TREE_PERIOD`), and how ray-cast callbacks are structured.
*   **For map compilation issues:** Open **BoundsTrait.TileAssembler** to trace how raw M2/WMO data is parsed, how bounds are calculated for models missing them, and how the binary output format is constructed.
*   **For static geometry behavior:** Open **BoundsTrait.WorldModel** to examine the `WorldModel`/`GroupModel` hierarchy, liquid interpolation logic (`WmoLiquid`), and the low-level ray-triangle intersection algorithms used for static objects.
