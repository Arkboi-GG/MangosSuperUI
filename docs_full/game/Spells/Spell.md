# Class Overview: Spell

**Identity:** The `Spell` class is the central runtime entity representing a single instance of a spell cast in the VMaNGOS server, managing its entire lifecycle from initialization and validation through effect execution and cleanup.

**Role in the System:**
`Spell` acts as the execution engine for the game’s magic and ability system. It bridges the static spell definitions (loaded from DBC files via `SpellEntry`) with the dynamic world state (`Unit`, `Player`, `Creature`, `GameObject`). When a player, creature, or bot casts a spell, a `Spell` object is instantiated to handle target resolution, resource consumption (mana, reagents, ammo), network synchronization (sending start/go/miss packets to clients), and the dispatching of specific effects (damage, healing, auras, summons). It is a transient object created per cast and destroyed upon completion or cancellation.

## How the Class is Split

The `Spell` class is implemented across two primary partials, separating the orchestration logic from the concrete effect implementations:

### Spell.Main
**Responsibility:** Lifecycle Orchestration & Validation  
This partial contains the core state machine and validation logic for a spell instance. It handles:
- **Construction & Destruction:** Initializing the spell with a caster, spell ID, and context (triggered vs. manual cast).
- **State Management:** Transitioning through states (`PREPARING`, `CASTING`, `DELAYED`, `FINISHED`) via methods like `prepare()`, `cast()`, `update()`, and `finish()`.
- **Target Resolution:** Determining valid targets for each effect using complex spatial queries (`FillTargetMap`, `SetTargetMap`) and validating them against game rules (`CheckTarget`, `CheckRange`).
- **Validation:** Enforcing cast requirements such as power costs, cooldowns, line-of-sight, stance/shapeshift restrictions, and item prerequisites (`CheckCast`, `CheckPower`, `CheckItems`).
- **Network Synchronization:** Sending opcode packets to clients to visualize casting progress, hits, misses, and channeling updates (`SendSpellStart`, `SendSpellGo`, `SendLogExecute`).
- **Resource Consumption:** Deducting mana, removing reagents, and consuming cast items or ammo (`TakePower`, `TakeReagents`, `TakeAmmo`).

### Spell.Effects
**Responsibility:** Concrete Effect Implementation  
This partial implements the specific game logic for every spell effect type defined in the World of Warcraft client protocol (Classic/1.12). It serves as the execution backend for `Spell.Main`.
- **Effect Handlers:** Contains ~130 methods named `Effect<Name>` (e.g., `EffectSchoolDMG`, `EffectApplyAura`, `EffectSummon`) that correspond to `SPELL_EFFECT_*` enum values.
- **Cross-Subsystem Integration:** Directly manipulates `Unit` health/power, applies/removes `Aura`s, summons `Creature`s or `GameObject`s, modifies player stats, and interacts with `BattleGround` systems.
- **Special Case Logic:** Handles hardcoded behaviors for specific spells (often via `switch` statements on Spell IDs within generic effects like `EffectDummy` or `EffectScriptEffect`).
- **Client Feedback:** Sends specific combat log packets and visual cues for effects like instant kills, resurrection requests, or lock picking.

## How the Partials Collaborate

The collaboration between `Spell.Main` and `Spell.Effects` follows a clear dispatcher pattern:

1.  **Initialization:** `Spell.Main` constructs the spell instance, validates the cast via `CheckCast()`, and consumes resources.
2.  **Target Resolution:** `Spell.Main` populates target lists (`m_UniqueTargetInfo`) by iterating through effects and resolving targets via `FillTargetMap()` and `SetTargetMap()`.
3.  **Dispatch:** During the `cast()` or `update()` phase, `Spell.Main` calls `HandleEffects()` or `DoAllEffectOnTarget()`. These methods iterate through the resolved targets and invoke the corresponding `Effect<Name>` method in `Spell.Effects` based on the spell’s effect index.
4.  **Execution:** `Spell.Effects` methods perform the actual game logic (e.g., dealing damage, applying auras). They often call back into `Spell.Main` for utility functions (e.g., `AddExecuteLogInfo`, `GetAffectiveCaster`) or modify external objects (`Unit`, `Player`).
5.  **Cleanup:** After all effects are processed, `Spell.Main` sends final network packets, updates threat/combat states, and destroys the `Spell` object.

**External Boundaries:**
- **Input:** Triggered by `Unit::CastSpell`, `Player::CastItemUseSpell`, or `Creature::TryToCast`.
- **Output:** Modifies `Unit`/`Player`/`Creature`/`GameObject` states, creates `Aura`/`Pet`/`DynamicObject` instances, and sends `WorldPacket`s to clients.
- **Dependencies:** Heavily relies on `SpellEntry` (static data), `SpellCaster` (caster utilities), `SpellMgr` (script/target bounds), and `ObjectMgr` (prototype data).

## Data Model

The `Spell` class **does not directly interact with database tables**. It operates entirely on in-memory objects and static data loaded at startup:
- **Static Data:** Reads from `SpellEntry` (DBC-derived) for spell definitions, effects, and attributes.
- **Dynamic State:** Modifies in-memory representations of `Unit`, `Player`, `Creature`, `GameObject`, and `Aura` objects.
- **Persistence:** Any database writes (e.g., saving pet state, updating character skills) are delegated to the respective owner objects (`Pet::SavePetToDB`, `Player::LearnSpell`), not performed by `Spell` itself.

## Where to Go Deeper

- **For Lifecycle & Validation:** Open **Spell.Main** to understand how spells are prepared, validated, targeted, and synchronized with clients. Key questions: "How does the server check if a player can cast this spell?" or "How are targets resolved for AoE spells?"
- **For Effect Logic:** Open **Spell.Effects** to see the implementation of specific spell behaviors. Key questions: "How does `EffectSchoolDMG` calculate damage?" or "How does `EffectSummon` create a pet?" or "What happens when `EffectDispel` is cast?"
