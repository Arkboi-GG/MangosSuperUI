# PlayerDumpReader

**PlayerDumpReader** is a utility class in the `wowvmangos` codebase responsible for importing a serialized player character state from a file into the database. It acts as the inverse of `PlayerDumpWriter`, allowing administrators to restore a character’s data—including inventory, mail, pets, and spells—from a previously generated dump file.

This unit is minimal: it defines only a constructor and one public method, `LoadDump`. The actual parsing and SQL execution logic resides in the corresponding `.cpp` implementation, which is not part of this documentation scope but is invoked via this interface.

## Purpose & Responsibilities

The sole purpose of **PlayerDumpReader** is to facilitate the restoration of a player character from a file-based backup. This is typically used for debugging, character recovery, or migration scenarios.

Key responsibilities:
1.  **File Ingestion:** Read a structured dump file generated by `PlayerDumpWriter`.
2.  **Data Restoration:** Parse the file and insert/update records into the `characters` database tables.
3.  **Error Reporting:** Return a `DumpReturn` code to indicate success or specific failure modes (e.g., file errors, data corruption).

## Member-by-Member Behavior

### Construction
*   **`PlayerDumpReader()`**: The default constructor initializes the reader object. It performs no I/O or database operations.

### Loading Logic
*   **`LoadDump(std::string const& file, uint32 account, std::string name, uint32 guid)`**: This is the core functional method. It accepts:
    *   `file`: Path to the dump file.
    *   `account`: The account ID for the character.
    *   `name`: The character’s name.
    *   `guid`: The unique identifier (GUID) for the character.
    
    It returns a `DumpReturn` value. The method handles the entire lifecycle of reading the file, parsing sections (defined by `DumpTableType` in the shared header), and executing the necessary SQL inserts/updates. It validates the file structure and ensures referential integrity across related tables (e.g., linking items in `character_inventory` to `item_instance`).

## Cross-Unit Boundaries

**PlayerDumpReader** integrates with the command handler system to expose its functionality to administrators.

*   **Called By: `ChatHandler.CharacterCommands/HandlePDumpLoadCommand`**
    *   **Direction:** Incoming call.
    *   **Context:** When an admin issues a command to load a player dump (e.g., `.pdump load`), the `ChatHandler` parses the arguments and instantiates a `PlayerDumpReader`.
    *   **Collaboration:** The `ChatHandler` delegates file parsing and database insertion to `PlayerDumpReader`. Upon return, the `ChatHandler` uses the `DumpReturn` code to notify the admin of success or failure.

*   **Calls Out:** None explicitly listed in the MAP. Internally, `LoadDump` interacts with the database connection pool (via `CharacterDatabase`) to execute SQL, but these are implementation details not exposed as separate members.

## Data Model

**PlayerDumpReader** interacts with the `characters` database. The `DumpTableType` enum in `PlayerDump.h` defines the scope of data restored:

1.  **Core Character (`DTT_CHARACTER`)**: `characters` table (`guid`, `name`).
2.  **Character State (`DTT_CHAR_TABLE`)**: `character_action`, `character_aura`, `character_homebind`, `character_queststatus`, `character_reputation`, `character_spell`, `character_spell_cooldown`, `character_tutorial`.
3.  **Inventory (`DTT_INVENTORY`)**: `character_inventory`.
4.  **Mail (`DTT_MAIL`, `DTT_MAIL_ITEM`)**: `mail`, `mail_items`, `item_text`.
5.  **Items (`DTT_ITEM`, `DTT_ITEM_GIFT`, `DTT_ITEM_LOOT`)**: `item_instance`, `character_gifts`, `item_loot`.
6.  **Pets (`DTT_PET`, `DTT_PET_TABLE`)**: `character_pet`, `pet_aura`, `pet_spell`, `pet_spell_cooldown`.
7.  **Item Text (`DTT_ITEM_TEXT`)**: `item_text`.

The reader ensures that all related records are inserted consistently, maintaining foreign key relationships where applicable.

## Notable Implementation Details

*   **Format Coupling:** The reader is tightly coupled to the output format of `PlayerDumpWriter`. Changes to the writer’s serialization logic require corresponding updates to the reader.
*   **GUID Management:** The `guid` parameter is passed by the caller (`ChatHandler`), implying the caller is responsible for ensuring the GUID is unique and available.
*   **Error Granularity:** The `DumpReturn` enum provides specific error codes (`DUMP_FILE_OPEN_ERROR`, `DUMP_TOO_MANY_CHARS`, `DUMP_UNEXPECTED_END`, `DUMP_FILE_BROKEN`), indicating robust validation during parsing.
