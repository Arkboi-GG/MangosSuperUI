# Creature

The `Creature` class is the server-side representation of non-player characters (NPCs), monsters, pets, and summons in the World of Warcraft 1.12.1 emulation. It extends the generic `Unit` combat and physics model with specific behaviors required for autonomous entities: lifecycle management (spawning, respawning, despawning), interaction interfaces (vendors, trainers, gossip), loot distribution, and AI-driven movement. Unlike `Player` objects, which are controlled by client input, `Creature` objects are driven entirely by server-side logic, making them the primary vehicle for world population, quest progression, and combat encounters.

The class is split into two partials to separate core entity state from the complex, stack-based movement system.

## How the class is split

### Creature.Main
This partial contains the core identity, state, and interaction logic of the creature. It manages:
*   **Lifecycle:** Creation from database records (`LoadFromDB`), memory allocation, and removal from the world (`RemoveFromWorld`, `DespawnOrUnsummon`).
*   **State & Stats:** Health, mana, death states, respawn timers, and stat initialization based on level and entry (`InitStatsForLevel`).
*   **Interactions:** Vendor inventory queries, trainer spell lists, gossip menu triggers, and quest relations.
*   **Combat & Loot:** Aggro ranges, threat management hooks, loot generation, and recipient determination (tapping).
*   **AI Integration:** Holding the `CreatureAI` pointer and providing hooks for AI updates, evade modes, and combat transitions.

### Creature.MotionMaster
This partial implements the movement engine for creatures. It uses a **stack-based system** of `MovementGenerator` objects to handle layered behaviors (e.g., a creature patrolling waypoints while simultaneously chasing a target). Key responsibilities include:
*   **Movement Stack Management:** Pushing/popping generators for actions like chasing, fleeing, following, or waypointing.
*   **State Transitions:** Switching between movement types (`MoveChase`, `MoveFleeing`, `MoveHome`) based on combat status or AI commands.
*   **Physics Integration:** Updating positions, handling splines, and managing expiration of temporary movements.
*   **Initialization:** Setting up default idle, random, or waypoint movements upon spawn or respawn.

## How the partials collaborate

`Creature.Main` acts as the decision-maker, while `Creature.MotionMaster` executes the physical movement. The collaboration follows a clear pattern:

1.  **AI-Driven Movement:** The `CreatureAI` (accessed via `Creature.Main::AI()`) decides *what* the creature should do (e.g., attack, flee, patrol). It then calls methods on `Creature.MotionMaster` (e.g., `MoveChase`, `MoveFleeing`) to enact that decision.
2.  **State Feedback:** `Creature.MotionMaster` provides feedback to the AI and Main logic via methods like `GetCurrentMovementGeneratorType()`, allowing the AI to know if the creature is currently moving, idle, or stuck.
3.  **Combat Integration:** When `Creature.Main` enters combat (`SetInCombatState`), it often triggers `Creature.MotionMaster` to switch to `MoveChase`. Conversely, when combat ends (`EnterEvadeMode`), `Creature.Main` instructs `MotionMaster` to return to home or default patrol.
4.  **External Triggers:** Scripts, spells, and player interactions (via `WorldSession`) modify `Creature.Main` state, which in turn updates `MotionMaster`. For example, a fear spell modifies the creature's state in `Main` and pushes a `FearMovementGenerator` onto the `MotionMaster` stack.

## Data model

The `Creature` class interacts with several database tables to persist state and define behavior:

*   **`creature`**: Stores static spawn data (position, entry ID, respawn time, movement type). Loaded at startup or on-demand via `LoadFromDB`.
*   **`creature_addon`**: Stores additional visual and behavioral data (display ID, mount, equipment, auras). Loaded via `LoadCreatureAddon`.
*   **`creature_movement`**: Defines waypoint paths for creatures. Used by `MotionMaster` when initializing waypoint generators.
*   **`creature_battleground`**: Links creatures to battleground events.
*   **`game_event_creature`** & **`game_event_creature_data`**: Manage creature spawns and modifications during game events.
*   **`smartlog_creature`**: Logs creature deaths and long combats for debugging and analysis.

## Where to go deeper

*   **Creature.Main**: Open this doc to understand how creatures are spawned, how they interact with players (vendors/trainers), how loot is calculated, and how AI is initialized. Essential for modding NPC behavior, loot tables, and spawn mechanics.
*   **Creature.MotionMaster**: Open this doc to understand how creatures move, how to debug pathfinding issues, and how different movement types (chase, flee, waypoint) interact. Essential for fixing AI movement bugs or creating custom movement behaviors.
