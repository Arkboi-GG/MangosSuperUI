# WorldPacket

## Purpose & Responsibilities

`WorldPacket` is the fundamental binary container for all network communication between the `wowvmangos` server and World of Warcraft clients. Inheriting from `ByteBuffer`, it encapsulates raw byte data with two protocol-specific metadata fields: a 16-bit **opcode** identifying the message type, and a 32-bit **timestamp** recording when the packet was received. It serves as the universal envelope for both incoming client commands and outgoing server updates, utilized by every subsystem from chat and movement to combat and inventory.

## Member-by-Member Behavior

### Construction & Initialization
*   **`WorldPacket()`**: Default constructor creating an empty packet with opcode `0` and no reserved buffer space. Used primarily when receiving data where the opcode is parsed later.
*   **`WorldPacket(uint16 opcode, size_t res)`**: Constructs a packet with a specific opcode and pre-allocates `res` bytes (default 200). This is the standard constructor for outgoing messages, allowing immediate opcode definition and memory reservation to avoid reallocation during serialization.
*   **`WorldPacket(const WorldPacket&)`**: Copy constructor duplicating the opcode, timestamp, and buffer contents. Used for broadcasting packets to multiple players or logging.
*   **`WorldPacket(WorldPacket&&)`**: Move constructor transferring ownership of the internal `ByteBuffer` storage, opcode, and timestamp. Essential for high-performance scenarios like queuing packets for asynchronous I/O, avoiding deep copies of large payloads.
*   **`Initialize(uint16 opcode, size_t newres)`**: Resets the packet: clears the buffer, reserves `newres` bytes, and sets the opcode. Allows object reuse for different message types without deallocation.

### Accessors & Mutators
*   **`GetOpcode()` / `SetOpcode(uint16)`**: Retrieve or set the 16-bit opcode. `GetOpcode` is used by `WorldSession` to dispatch incoming packets to handlers; `SetOpcode` defines the message type for outgoing packets.
*   **`GetPacketTime()` / `FillPacketTime(uint32)`**: Retrieve or set the 32-bit reception timestamp. `FillPacketTime` is called by `WorldSocket` upon successful packet receipt; `GetPacketTime` supports latency analysis and anti-cheat validation.

### Assignment
*   **`operator=(WorldPacket&&)`**: Move assignment operator transferring opcode, timestamp, and buffer state from the right-hand side. Used in packet queues and state swaps.

## Cross-Unit Boundaries

`WorldPacket` is the primary interface between the network layer (`WorldSocket`, `WorldSession`) and game logic.

*   **Outgoing (Server → Client)**: Nearly all game logic units construct `WorldPacket` instances to send updates.
    *   **High-Frequency Updates**: `MovementPacketSender`, `Unit.Main`, and `MoveSplineInit` create packets for position/speed changes. They often use `Initialize` or move semantics to minimize allocation overhead.
    *   **Game Events**: `BattleGroundMgr`, `game_Group_Group`, `Spell.Main`, and `Player.Main` construct packets for discrete events (joins, spells, loot). They typically use the `WorldPacket(uint16, size_t)` constructor.
    *   **Chat & Social**: `ChatHandler.Chat`, `game_Chat_Channel`, and `SocialMgr` build packets for messages and friend lists.
*   **Incoming (Client → Server)**:
    *   **Receipt**: `WorldSocket` reads raw data into a `WorldPacket` and calls `FillPacketTime`.
    *   **Dispatch**: `WorldSession.Main` extracts the opcode via `GetOpcode()` to route the packet to specific handlers (e.g., `HandleChatMessageOpcode`).
    *   **Analysis**: `SniffFile`, `MovementAnticheat`, and debug commands inspect `WorldPacket` contents using `GetOpcode` and `GetPacketTime` for logging and validation.

## Data Model

`WorldPacket` does not interact with any database tables. It is a transient, in-memory structure.

## Notable Implementation Details

1.  **Endianness**: The header notes that `m_opcode` and size are stored in platform-dependent format. Endian conversion is deferred to the network layer (`WorldSocket`/`ByteBuffer`) at send/receive time, optimizing internal serialization speed.
2.  **Move Semantics Safety**: The move constructor explicitly copies `m_opcode` and `m_recvdTime` before moving the `ByteBuffer` storage. While the source packet's state becomes undefined after a move, the destination packet retains valid metadata. A `TODO` comment warns about technical illegality if the source is accessed post-move, but the current implementation ensures the destination is fully initialized.
3.  **Buffer Reuse**: `Initialize` enables packet object pooling/reuse, critical for reducing heap fragmentation in high-throughput paths like movement updates.
