# Object Hierarchy Reference Documentation

This document describes the `Object` class hierarchy within the `wowvmangos` codebase. This hierarchy forms the foundational data model for all entities existing in the game world, including players, creatures, game objects, corpses, and spell effects.

The hierarchy is structured as follows:
1.  **`Object`**: The abstract base class defining identity, GUIDs, basic state flags, and update field management.
2.  **`WorldObject`**: Inherits from `Object`. Adds spatial properties (position, map ID), visibility logic, and network communication capabilities for entities that exist in the 3D world.
3.  **`SpellCaster`**: Inherits from `WorldObject`. Adds spell casting mechanics, cooldown management, and damage/healing calculation interfaces.
4.  **`Unit`**: Inherits from `SpellCaster`. Represents living entities capable of combat, movement, and having health/power. Includes `Creature`, `Player`, and `Pet`.
5.  **`GameObject`**: Inherits from `SpellCaster`. Represents static or interactive world elements like doors, chests, and quest items.
6.  **`Corpse`**: Inherits from `WorldObject`. Represents dead bodies and loot containers.

## Purpose & Responsibilities

The primary responsibility of this unit is to provide a unified interface for managing entity lifecycle, identity, state synchronization with clients, and type-safe downcasting.

*   **Identity Management**: Every entity possesses a unique Global Unique Identifier (GUID) composed of a high part (type/map) and a low part (counter). The `Object` class manages these GUIDs and provides methods to retrieve them in various formats (raw uint64, string, packed).
*   **State Synchronization**: The game server must keep client representations of entities up-to-date. The `Object` class maintains arrays of "Update Fields" (health, power, flags, etc.) and tracks changes via `UpdateMask`s. It provides methods to build network packets (`BuildValuesUpdate`, `BuildCreateUpdateBlock`) that transmit these changes to players.
*   **Type Safety**: Since all entities share a common base, polymorphism is heavily used. The `Object` class provides `IsType()` checks and `To<Type>()` casting methods (e.g., `ToPlayer()`, `ToCreature()`) to safely navigate the hierarchy.
*   **World Presence**: The `WorldObject` subclass manages whether an entity is currently "in the world" (`IsInWorld()`), its physical coordinates, and its visibility to other players.

## Member-by-Member Behavior

### Identity and Type Checking

*   **`GetGUID`**, **`GetGUIDLow`**, **`GetObjectGuid`**, **`GetPackGUID`**, **`GetGuidStr`**: Retrieve the entity's unique identifier. `GetGUID` returns the raw 64-bit integer. `GetGUIDLow` returns the lower 32 bits (often used for database keys or quick comparisons). `GetObjectGuid` returns the structured `ObjectGuid` object. `GetPackGUID` returns a compressed version for network transmission. `GetGuidStr` returns a human-readable string representation.
*   **`GetEntry`**, **`SetEntry`**: Retrieve or set the entity's "Entry" ID. This is a database key linking the runtime object to static configuration data (e.g., `creature_template`, `gameobject_template`).
*   **`GetTypeId`**, **`GetTypeMask`**, **`IsType`**: Determine the specific kind of object. `GetTypeId` returns a specific enum (e.g., `TYPEID_PLAYER`). `GetTypeMask` returns a bitmask allowing broader categorization (e.g., `TYPEMASK_UNIT` covers players, creatures, and pets). `IsType` checks if the object matches a specific mask.
*   **`ToPlayer`**, **`ToCreature`**, **`ToUnit`**, **`ToGameObject`**, **`ToCorpse`**, **`ToPet`**, **`ToSpellCaster`**, **`ToWorldObject`**: Safe downcasting methods. They first verify the type using `IsType` or similar checks, then perform a `static_cast`. If the type doesn't match, they return `nullptr`. This prevents undefined behavior from invalid casts.

### Lifecycle and World State

*   **`AddToWorld`**, **`RemoveFromWorld`**: Control the entity's presence in the game world. `AddToWorld` sets the `m_inWorld` flag to true and clears any pending update masks, ensuring a clean state for creation packets. `RemoveFromWorld` sets `m_inWorld` to false and clears update masks, signaling that the object should no longer send updates.
*   **`IsInWorld`**: Returns the boolean `m_inWorld` flag. Many systems check this before performing operations to ensure the object is active.
*   **`IsDeleted`**: Returns the `m_deleted` flag, indicating if the object is scheduled for removal from the world (often used in deferred deletion patterns to avoid iterator invalidation during iteration).

### Update Fields and State Modification

The `Object` class manages several parallel arrays (`m_int32Values`, `m_uint32Values`, `m_floatValues`) that store the entity's state. These correspond to fields defined in the client-server protocol.

*   **`GetInt32Value`**, **`GetUInt32Value`**, **`GetUInt64Value`**, **`GetFloatValue`**, **`GetByteValue`**, **`GetUInt16Value`**, **`GetInt16Value`**, **`GetGuidValue`**: Accessors for the underlying value arrays. They include assertions to prevent out-of-bounds access.
*   **`SetInt32Value`**, **`SetUInt32Value`**, **`SetUInt64Value`**, **`SetFloatValue`**, **`SetByteValue`**, **`SetUInt16Value`**, **`SetInt16Value`**, **`SetGuidValue`**: Mutators for the value arrays. These typically mark the corresponding index in the `UpdateMask` as dirty, triggering a network update.
*   **`ApplyModUInt32Value`**, **`ApplyModInt32Value`**, **`ApplyModPositiveFloatValue`**, **`ApplyModSignedFloatValue`**: Apply additive modifiers to values. Used extensively by auras and buffs to temporarily modify stats.
*   **`ApplyPercentModFloatValue`**: Applies a percentage-based modifier to a float value.
*   **`SetFlag`**, **`RemoveFlag`**, **`ToggleFlag`**, **`HasFlag`**: Bitwise operations on 32-bit unsigned integer fields. Used for flags like `UNIT_FLAG_PVP` or `GAMEOBJECT_FLAG_LOCKED`.
*   **`SetByteFlag`**, **`RemoveByteFlag`**, **`ToggleByteFlag`**, **`HasByteFlag`**: Bitwise operations on individual bytes within a 32-bit field.
*   **`SetShortFlag`**, **`RemoveShortFlag`**, **`ToggleShortFlag`**, **`HasShortFlag`**: Bitwise operations on 16-bit halves of a 32-bit field.
*   **`SetFlag64`**, **`RemoveFlag64`**, **`ToggleFlag64`**, **`HasFlag64`**: Bitwise operations on 64-bit fields.
*   **`ApplyModFlag`**, **`ApplyModByteFlag`**, **`ApplyModShortFlag`**, **`ApplyModFlag64`**: Conditional flag setting/removal based on a boolean `apply` parameter.

### Network Updates

*   **`BuildCreateUpdateBlockForPlayer`**: Constructs the initial packet sent to a player when an object first becomes visible to them.
*   **`BuildValuesUpdateBlockForPlayer`**: Constructs packets containing only the fields that have changed since the last update.
*   **`BuildOutOfRangeUpdateBlock`**: Constructs a packet indicating the object has moved out of range or despawned.
*   **`BuildMovementUpdateBlock`**: Constructs packets containing movement spline data.
*   **`MarkForClientUpdate`**: Flags the object to be included in the next global update cycle.
*   **`AddDelayedAction`**: Queues actions (like marking for update or adding to remove lists) to be executed later, often to avoid modifying collections during iteration.

### Spatial and World Properties (WorldObject)

*   **`GetPosition`**, **`GetX`**, **`GetY`**, **`GetZ`**, **`GetOrientation`**: Retrieve the entity's 3D coordinates and rotation.
*   **`Relocate`**: Changes the entity's position. This is a heavy operation that may trigger visibility updates and cell migrations.
*   **`GetMapId`**, **`GetInstanceId`**: Identify which map and instance the object resides in.
*   **`GetDistance`**, **`GetDistance2d`**, **`GetDistance3d`**: Calculate Euclidean distances to other objects or coordinates.
*   **`IsWithinDist`**, **`IsWithinLOS`**: Check proximity and line-of-sight constraints.
*   **`SendMessageToSet`**: Broadcasts a network packet to all players who currently have this object in their visible list.

## Cross-Unit Boundaries

The `Object` hierarchy is central to the engine, interacting with nearly every other subsystem.

*   **`Map.Main`**: The `Map` class manages grids and cells. `Object::AddToWorld` and `RemoveFromWorld` interact with `Map` to register/unregister objects in the appropriate grid cells. `Map::Update` iterates over objects to call their `Update` methods.
*   **`Player.Main`**: Players are the primary observers of objects. `Player::UpdateVisibilityOf` relies on `Object::IsVisibleForInState` to determine what a player sees. `Player::GetItemByGuid` and similar methods rely on `Object::GetGUID` to identify items.
*   **`Unit.Main`**: As a subclass, `Unit` inherits all `Object` functionality. `Unit::Attack` uses `Object::GetDistance` to check range. `Unit::DealDamage` uses `Object::GetUInt32Value` to read health.
*   **`Creature.Main`**: Creatures use `Object::SetEntry` to change their appearance or behavior dynamically. `Creature::Respawn` uses `Object::AddToWorld` to bring the creature back.
*   **`GameObject.Main`**: Game objects use `Object::GetEntry` to determine their type (door, chest, etc.). `GameObject::Use` interacts with `Player` via `Object::SendMessageToSet` to provide feedback.
*   **`Spell.Main`**: Spells target objects. `Spell::CheckCast` verifies targets using `Object::IsType` and `Object::GetGUID`. `Spell::EffectDummy` often modifies object fields using `Object::SetUInt32Value`.
*   **`WorldSession.Main`**: Handles network packets. When a player selects an object, `WorldSession` uses `Object::GetGUID` to identify the target. When an object updates, `WorldSession` sends the resulting packets to the client.
*   **`LootMgr`**: Loot generation depends on `Object::GetEntry` to look up loot tables. `LootMgr::FillPlayerDependentLoot` checks `Object::IsPlayer` to determine if the looter is a player.

## Data Model

The `Object` hierarchy does not directly interact with database tables in this unit. However, the `Entry` ID retrieved via `GetEntry()` corresponds to primary keys in static template tables such as `creature_template`, `gameobject_template`, and `item_template`. The runtime state (health, position, flags) is transient and exists only in memory, though `Player` and `Corpse` subclasses persist specific fields to the database upon logout or death.

## Notable Implementation Details

*   **Union of Value Arrays**: The `Object` class uses a `union` for `m_int32Values`, `m_uint32Values`, and `m_floatValues`. This allows accessing the same memory location as different types, which is efficient but requires careful handling to avoid type confusion. The indices are carefully mapped to match the client protocol.
*   **Update Mask Optimization**: To minimize network traffic, the `Object` class tracks which fields have changed using an `UpdateMask`. Only dirty fields are included in update packets. This is crucial for performance in areas with many players and objects.
*   **Deferred Deletion**: Objects are not immediately deleted when `RemoveFromWorld` is called. Instead, they are marked as deleted and added to a removal list. This prevents iterator invalidation when iterating over object lists during the update loop. The actual deletion happens in a subsequent cleanup phase.
*   **Thread Safety**: While the core `Object` methods are not inherently thread-safe, access to objects is generally serialized through the `Map` update loop. However, some fields like `m_visibleGUIDs` in `Player` use mutexes to protect concurrent access from different threads (e.g., network thread vs. update thread).
*   **GUID Structure**: The GUID is a 64-bit value. The high 32 bits encode the type and map/instance information. The low 32 bits are a unique counter. This structure allows for quick type checking and map identification without dereferencing the object.
